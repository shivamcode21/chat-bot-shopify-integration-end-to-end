## 1. Executive Summary

This document specifies a queue-based asynchronous processing pipeline built on
**[Dramatiq](https://dramatiq.io/) + a dedicated Redis broker**. Incoming
webhooks (Shopify, Shiprocket, Delhivery) are acknowledged at the edge and
their heavy work is offloaded to dedicated worker processes that drain the
queues at a rate matched to **DB-pool / CPU capacity**, not to the inbound
request rate.

Goals:

- ✅ **Survive bursts without horizontal sprawl** — a sudden storm (the incident
  was ~4,550 webhooks in ~35 min, peak ~5 req/s) lands in a durable queue and is
  drained by a **small, fixed** worker footprint. Autoscale only on an SLO breach.
- ✅ **Never exhaust the DB pool from the request path** — webhook endpoints do
  no DB work; they enqueue and return `200`. This structurally removes the
  pool-exhaustion → upstream-502 failure mode.
- ✅ **Consumer-group model** — one queue per source/type; workers subscribe to
  specific queues so an inventory storm cannot starve product/order/shipping.
- ✅ **A general background-task platform** — the same machinery runs *all*
  deferred work: delta product-sync crons, escalation messages, Shopify
  order-note/tag writes, message tagging, and outbound events/templates — not
  just webhooks (see §16).
- ✅ **At-least-once with idempotency** — ack/heartbeat requeue on worker crash,
  bounded retries, dead-letter queue, and dedup on the webhook/shipment id.

This **supersedes PR #666**, whose hand-rolled `LPUSH`/`BRPOP` queue lacked
acknowledgement/visibility, queue isolation, idempotency, and DLQ tooling, and
whose fire-and-forget audit write still ran on the web event loop against the
shared DB pool.

## 2. Problem Statement

### 2.1 The incident

A Grafana alert fired: **204 × HTTP 502 in 30 min** on
`ecommagents-webhook-handlers` (threshold 10). Investigation showed:

- The app's own access logs had **only 200s + one 405 — no 5xx**. The 502s were
  generated by the **upstream proxy (Render)** while workers were blocked, not
  returned by the app.
- A burst of Postgres pool timeouts: `couldn't get a connection after 15.00 sec`.
- A **Shopify webhook storm**: ~4,550 webhooks in ~35 min (3,251 inventory +
  1,275 product), peak ~1,467 / 5 min. Both app instances saturated their pools.

### 2.2 Root cause

Webhooks were processed **synchronously inline**. Each request awaited heavy
enrichment + DB work — including a *non-critical* `product_sync_logs` audit
INSERT — while holding a pooled connection. With `DB_POOL_MAX=30`
(`database_manager.py`), the burst exhausted the pool; handlers blocked up to the
pool timeout and the proxy returned 502. Shopify then retried, compounding the
storm.

### 2.3 Why this recurs without a structural fix

The request path and the DB are coupled: inbound rate directly drives concurrent
DB connection demand. Any source (Shopify/Shiprocket/Delhivery) bursting past
`DB_POOL_MAX` concurrent jobs takes the service down. The fix must **decouple
ingestion rate from processing rate**.

## 3. Why Dramatiq

Dramatiq is a good fit for this **async-first** codebase (handlers like
`handle_product_upsert`, `_handle_inventory_level_update`, and the
shiprocket/delhivery/order event processors are all `async def`):

1. **AsyncIO middleware** runs one event-loop thread per worker process; each
   worker *thread* submits a coroutine and awaits its result. The practical
   consequence: **`--threads N` is a hard ceiling on concurrent in-flight jobs**
   per process — precisely the knob we need to bound DB-pool pressure. Existing
   `async` handlers become actors nearly verbatim.
   ([asyncio middleware source](https://dramatiq.io/_modules/dramatiq/middleware/asyncio.html))
2. **Built-in reliability**: Retries middleware with exponential backoff
   (`max_retries`, `min_backoff`, `max_backoff`), dead-lettering, and
   **ack + heartbeat-based requeue** so a crashed worker's in-flight message is
   redelivered (the hand-rolled `BRPOP` in PR #666 drops it).
   ([guide](https://dramatiq.io/guide.html))
3. **Per-actor `queue_name` + `priority` + `time_limit`**, and workers can serve
   a **subset of queues** via `--queues` — the basis of our consumer-group model.
4. **Redis-backed rate limiters** (`WindowRateLimiter`, `ConcurrentRateLimiter`)
   for the outbound-notification lane. ([cookbook](https://dramatiq.io/cookbook.html))

## 4. Why a Dedicated Broker Redis

**The Dramatiq broker must NOT be the Upstash instance** used for state/cache
(`utils/redis_client.py`):

- Dramatiq's Redis broker drives dispatch through a **polling Lua script** with a
  maintenance/heartbeat loop. Serverless Redis has broken this before — AWS
  ElastiCache Serverless is documented as incompatible (*"KEYS is not supported
  on Serverless, and Lua scripts without any input keys are not supported"* —
  [Bogdanp/dramatiq#754](https://github.com/Bogdanp/dramatiq/issues/754)).
- Upstash is also serverless and **bills per command**. Continuous dispatch
  polling by every worker would be a constant, scaling cost.

**Decision:** use a dedicated **Render Key Value** instance (paid tier) for the
broker, configured via a new `DRAMATIQ_BROKER_URL`. The existing Upstash
`REDIS_URL` continues to back state/cache and the rate-limiter backend
(occasional traffic, serverless-friendly).

### 4.1 Why Render Key Value fits (it is *not* serverless)

Render Key Value is a **dedicated, managed instance** (new instances run
**Valkey 8**, a drop-in Redis 7.2.4 fork), billed at a **flat per-instance
price** by memory tier — *not* per-command like Upstash. It exposes the **full
command set** (Lua `EVAL`, `BLPOP`, etc.), so Dramatiq's polling Lua-dispatch
broker works without serverless caveats and without per-command cost. Render
**explicitly recommends Key Value for job queues**.

| | Upstash (state/cache) | Render Key Value (broker) |
|---|---|---|
| Model | Serverless | Dedicated managed instance |
| Billing | Per-command | Flat (per memory tier) |
| Lua `EVAL` / `BLPOP` | serverless caveats | Full Valkey command set |
| Persistence | managed | Disk-backed (`appendfsync everysec`) on paid |
| Job-queue fit | poor (polling cost) | Recommended for job queues |

### 4.2 Operational requirements (must-haves, not defaults)

1. **Paid tier only.** Free Key Value (25 MB / 50 conns) has **no persistence**
   — all queued jobs are lost on restart. Unacceptable for a broker.
2. **`maxmemory-policy = noeviction`** (Render's own job-queue recommendation):
   under a deep backlog, the default eviction policies would silently drop
   queued jobs. With `noeviction`, enqueues fail loudly and the bounded inline
   fallback (§7.1) catches them.
3. **Connection budget.** `Σ(worker_processes × threads) + headroom` must fit the
   instance's connection cap (couples to §9 sizing).
4. **Single instance = SPOF**, and `appendfsync everysec` means up to ~1s of
   writes can be lost on a hard crash. Acceptable here because sources
   (Shopify/Shiprocket/Delhivery) retry for hours and the idempotency guard
   (§10) + bounded inline fallback (§7.1) absorb both — but stated explicitly so
   it is a conscious trade-off. Revisit an HA tier if the broker becomes
   business-critical.

## 5. Proposed Architecture

```
                         ┌──────────────────────────────────────────┐
  Shopify  ─┐            │              WEB TIER (FastAPI)            │
 Shiprocket ┼─ webhook ─▶│  verify → validate → actor.send() → 200   │  (no DB work)
  Delhivery ┘            └───────────────────┬──────────────────────┘
                                             │ enqueue (Dramatiq .send)
                                             ▼
                              ┌──────────────────────────────┐
                              │   Dedicated Redis (broker)    │
                              │  per-lane queues + DLQ        │
                              └───────────────┬──────────────┘
     ┌───────────┬───────────┬───────────┼───────────┬───────────┬───────────┐
     ▼           ▼           ▼           ▼           ▼           ▼           ▼
 ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐  ┌────────┐  ┌──────────┐
 │inventry│  │product │  │ order  │  │  cart  │  │shiprckt│  │delhvry │  │ outbound │
 │  t=8   │  │  t=4   │  │  t=3   │  │  t=2   │  │  t=2   │  │  t=2   │  │ t=4 (RL) │
 └───┬────┘  └───┬────┘  └───┬────┘  └───┬────┘  └───┬────┘  └───┬────┘  └────┬─────┘
     └─────────── one worker SERVICE per lane · own threads / DB pool ────────┘
              (+ worker-sync for product_sync) · existing async handlers unchanged
                                             │
                                             ▼
                                      Postgres (budgeted max_connections)
```

The web tier and each worker process keep **exactly one** shared async Redis
client (Upstash, per AGENTS.md §4.4) for state/dedup, plus their own asyncpg
pool. The Dramatiq broker connection is owned by Dramatiq, separate from both.

## 6. Queue Topology

One queue per source/type ("consumer-group" model). A storm in one lane never
starves another, and each lane gets its own priority and worker budget. The
`Trigger` column shows that the *same* queue/actor/worker machinery serves
edge- (webhook), schedule- (cron), and app-triggered work — see §16 for the
non-webhook patterns.

| Queue | Trigger | Feeds | Priority | Notes |
|---|---|---|---|---|
| `webhooks.shopify.inventory` | edge | inventory level updates | low | highest-volume, burstiest |
| `webhooks.shopify.product` | edge | product create/update/delete | normal | heavier per-job (enrichment + vector sync) |
| `webhooks.shopify.order` | edge | order create/update/cancel | high | customer-facing |
| `webhooks.shopify.cart` | edge | abandoned checkout / cart (`/cart/checkout/webhook`) | high | latency-sensitive (nudges are worthless if delayed) |
| `webhooks.shiprocket` | edge | shipment status | high | customer-facing |
| `webhooks.delhivery` | edge | shipment status | high | customer-facing |
| `product_sync` | cron + app | delta + bulk/catalog sync jobs | low | long-running, off-peak; per-client fan-out (§16.4) |
| `shopify.writes` | app | order-note updates, order tagging → Shopify Admin API | normal | per-shop API rate limit + per-order serialization (§16.6) |
| `messages.tagging` | app | classify/label conversation messages | low | DB write; batchable; naturally idempotent |
| `outbound.escalations` | app | escalation messages to client | high | customer-facing; messaging rate limit |
| `outbound.notifications` | app | events/templates → user | normal | **rate-limited** to WhatsApp/Gupshup caps |

> Dramatiq priority orders messages *after* a worker has pulled them; queue
> separation (not priority alone) is what gives true lane isolation. We use both.
> **Group queues by the resource they contend on**, not just by feature: every
> task writing to the Shopify Admin API shares `shopify.writes` so one per-shop
> rate limiter governs all of it; everything sent to the user shares the
> messaging rate limiter. `outbound.escalations` is split from
> `outbound.notifications` only because it is customer-critical (higher
> priority), though both honour the same messaging budget.

## 7. Producer (edge) Design

Each webhook route is reduced to: **authenticate (HMAC/token) → minimal validate
→ `actor.send(...)` → return `200`.** No DB calls, no shared-async-pool work on
the request path.

```python
# fashion_bot/shopify/webhook/product_webhook.py  (illustrative)
from fashion_bot.workers.actors import inventory_update, product_upsert

@router.post("/webhook/inventory")
async def inventory_webhook(request: Request, client_id: str = None):
    payload = await _verify_and_extract(request)          # HMAC + parse only
    enqueue_or_inline(
        inventory_update,
        kwargs=dict(inventory_item_id=payload.item_id,
                    client_id=payload.client_id,
                    shopify_webhook_id=payload.webhook_id,
                    shopify_shop_domain=payload.shop_domain),
        inline=lambda: _handle_inventory_level_update(...),  # bounded fallback
    )
    return {"status": "ok"}
```

### 7.1 Enqueue-failure behavior (bounded inline fallback)

Per decision, when the broker is **unreachable** at enqueue time we **fall back
to inline processing** (PR #666 behavior) so a webhook is never dropped — **but
bounded** so it cannot reproduce the original pool exhaustion:

- `enqueue_or_inline` attempts `actor.send()` with a short bounded retry.
- On failure, inline execution is gated by a **process-wide `asyncio.Semaphore`**
  (`WEBHOOK_INLINE_MAX_CONCURRENCY`, e.g. 5 — well under `DB_POOL_MAX`).
- If the semaphore is saturated (a storm *and* the broker is down simultaneously),
  the endpoint returns fast (`503`/`200-deferred`) and relies on the source's
  own retry (Shopify/Shiprocket retry for hours).

> ⚠️ **Reviewer note:** unbounded inline fallback was the failure mode in the
> original incident. The semaphore is the safeguard that lets us keep the
> "never drop" guarantee without re-opening the 502 hole. Flag if you want pure
> inline (no cap) or pure enqueue-only (no fallback) instead.

## 8. Actor & Worker Design

**Principle: one handler + one actor + one queue per webhook type — shared
plumbing only.** Each type (product, inventory, order, cart/checkout, shiprocket,
delhivery) keeps its own dedicated async handler because the types have
genuinely different semantics: idempotency/safety (inventory = idempotent
overwrite; orders touch billing/fulfillment; cart nudges are time-sensitive),
cost/limits (product enrichment + vector sync is heavy; inventory is light but
burstiest), payload schemas, and failure domains (a product-enrichment bug must
not dead-letter order webhooks). What is shared is the *plumbing* — the
`enqueue_or_inline` helper, the broker module, the idempotency guard, and
observability — so per-type separation does not mean duplicated retry/dedup
boilerplate.

Actors are thin wrappers over the **existing** async handlers:

```python
# fashion_bot/workers/actors.py
import dramatiq
from fashion_bot.workers.broker import broker          # sets dramatiq broker + AsyncIO middleware

@dramatiq.actor(queue_name="webhooks.shopify.inventory",
                max_retries=5, min_backoff=500, max_backoff=300_000,
                time_limit=60_000)
async def inventory_update(*, inventory_item_id, client_id,
                           shopify_webhook_id=None, shopify_shop_domain=None):
    if await already_processed(shopify_webhook_id):       # idempotency guard
        return
    from fashion_bot.shopify.webhook.product_webhook import _handle_inventory_level_update
    await _handle_inventory_level_update(
        inventory_item_id=inventory_item_id, client_id=client_id,
        trace_id=current_trace_id(),
        shopify_webhook_id=shopify_webhook_id,
        shopify_shop_domain=shopify_shop_domain,
    )
```

- **Broker module** (`workers/broker.py`): constructs `RedisBroker(url=DRAMATIQ_BROKER_URL)`,
  adds `AsyncIO`, `Retries`, and (for outbound) rate-limiter middleware. Imported
  by both producer and worker so actor definitions are shared.
- **Per-process resources**: each worker process initializes its own asyncpg pool
  (small `DB_POOL_MAX`) and its own shared async-redis client on its own loop —
  AGENTS.md §4.4 stays satisfied (one async client *per process*).
- **Worker entrypoint**: standard `dramatiq fashion_bot.workers.actors --queues <lanes>`;
  each Render worker service passes the lanes it owns.

## 9. Backpressure & Capacity Model

This is the heart of "process as DB/CPU allows, scale only if forced."

**Invariant:** total concurrent jobs across all workers ≤ a safe Postgres
connection budget. Concurrency is set by `processes × threads`, **not** node
count.

- Each worker process holds its own asyncpg pool; **threads per worker ≤ its
  pool size**, so a worker can never demand more connections than it holds.
- Budget `max_connections` across all services. Example starting point:

  | Service | Processes | Threads | DB pool/proc | Peak DB conns |
  |---|---|---|---|---|
  | Web | (gunicorn) | — | 30 | 30 |
  | `worker-inventory` | 1 | 8 | 8 | 8 |
  | `worker-product` | 1 | 4 | 4 | 4 |
  | `worker-order` | 1 | 3 | 3 | 3 |
  | `worker-cart` | 1 | 2 | 2 | 2 |
  | `worker-shiprocket` | 1 | 2 | 2 | 2 |
  | `worker-delhivery` | 1 | 2 | 2 | 2 |
  | `worker-sync` | 1 | 2 | 2 | 2 |
  | `worker-outbound` | 1 | 4 | 3 | 3 |
  | **Total** | | | | **≈ 56** (set Postgres `max_connections` ≥ 100 with headroom) |

- **One worker service per lane (day one).** Each lane gets its own process, so
  its threads/pool/priority are tuned independently and a storm or a bad deploy
  in one lane is fully isolated. Threads per worker ≤ its pool size (a worker can
  never demand more connections than it holds).
- **Watch idle-pool cost.** With 8 worker processes each holding a pool, set
  `WORKER_DB_POOL_MIN=1` so idle lanes don't pin connections; pools grow on
  demand up to their max during a burst.
- **Budget broker connections too.** Each worker opens connections to the Render
  Key Value broker; `Σ(workers × threads) + overhead` must fit the instance's
  connection cap (§4.2). Low-volume lanes (cart, shiprocket, delhivery, sync) run
  on the **smallest instance size** — separation is about isolation, not spend.
- During a burst the **queue absorbs** the spike; latency rises briefly, nothing
  falls over. Throughput is bounded and predictable.
- **Autoscale only on an SLO breach** — per-lane queue depth or oldest-message
  age over a threshold — never on raw inbound request rate. This is "only if
  urgently required."

## 10. Reliability: Retries, DLQ, Idempotency

- **Retries**: per-actor `max_retries` with exponential backoff via the Retries
  middleware. Transient failures (e.g. a brief DB blip) self-heal.
- **Ack + heartbeat requeue**: if a worker crashes mid-job, the Redis broker's
  heartbeat timeout causes the in-flight message to be redelivered — no silent
  loss (the PR #666 `BRPOP` removed the job immediately on pop).
- **Dead-letter queue**: messages exhausting retries are dead-lettered (Dramatiq
  retains them with a TTL). We add a small **DLQ replay command**
  (`python -m fashion_bot.workers.dlq replay --queue ...`).
- **Idempotency** (closes PR #666's deferred follow-up): at-least-once delivery +
  source retries ⇒ each actor first checks a dedup guard
  (`SET NX webhook:seen:{id} EX <ttl>` on Upstash). Already-processed ⇒ no-op.

## 11. Outbound Notifications & Rate Limiting

The `outbound.notifications` queue buffers events/templates before they are sent
to users. A Dramatiq **`WindowRateLimiter`** (Redis-backed) enforces WhatsApp /
Gupshup per-second and per-day caps even during a large fan-out, replacing
ad-hoc throttling. Failed sends retry with backoff; permanent failures
dead-letter for inspection.

| `ecommagents-worker-shiprocket` | Background Worker | `dramatiq fashion_bot.workers.actors --queues webhooks.shiprocket --threads 2` |

smallest instance — the separation buys isolation, not extra spend. The two
`--threads` knobs to watch in production are `worker-inventory` (burstiest) and
`worker-product` (heaviest per-job).

## 13. How This Fixes PR #666

| PR #666 issue | This design |
|---|---|
| Hand-rolled `LPUSH`/`BRPOP` — **no ack/visibility**; worker crash mid-job silently drops the webhook | Dramatiq ack + heartbeat requeue redelivers in-flight messages |
| `submit_or_inline` **unbounded inline fallback** re-runs heavy DB work on the web tier when Redis is down — reproduces pool exhaustion | Inline fallback retained but **semaphore-bounded**; beyond the cap, defer to source retry |
| Fire-and-forget `asyncio.create_task` audit write still runs **on the web loop + DB pool**, just unawaited; piles up under a storm | Audit writes become queued jobs off the web tier |
| Single FIFO list — inventory storm starves product/order updates | Per-source/type queues + priorities + per-lane workers |
| Shared-vs-dedicated async-client debate (the whole §4.4 back-and-forth) | Dramatiq owns its broker connection; §4.4 untouched |
| No idempotency (acknowledged follow-up) | Dedup guard on webhook/shipment id |
| No DLQ replay tooling | Dramatiq DLQ + replay command |
| Polling on serverless Upstash (per-command cost / compatibility) | Dedicated persistent broker Redis |

## 14. Migration & Rollout

Lane by lane, mirroring PR #666's "default-off, deploy-inert" safety:

1. **Land code + broker, flag off.** `WEBHOOK_QUEUE_ENABLED=false` → endpoints
   behave exactly as today (inline). Provision `dramatiq-broker`.
2. **Stand up worker services** (start commands above), idle until enabled.
3. **Enable inventory lane first** (it was the storm source): route only
   `inventory` through `enqueue_or_inline`. Watch queue depth, latency, DB pool.
4. **Enable product/order lanes**, then shipping.
5. **Migrate product-sync and outbound** onto their queues.
6. **Load test** an inventory burst: assert no `couldn't get a connection`, no
   502s, throughput scales with worker threads, DLQ stays empty.

Rollback at any step = flip the per-lane flag off → inline behavior returns.

## 15. Configuration Reference

| Var | Default | Purpose |
|---|---|---|
| `DRAMATIQ_BROKER_URL` | — | dedicated Render Key Value broker (paid, `noeviction`; NOT Upstash) |
| `WEBHOOK_QUEUE_ENABLED` | `false` | master switch: enqueue vs inline |
| `WEBHOOK_QUEUE_LANES` | `inventory` | comma list of lanes routed through the queue |
| `WEBHOOK_INLINE_MAX_CONCURRENCY` | `5` | semaphore cap for inline fallback |
| `WEBHOOK_ENQUEUE_MAX_ATTEMPTS` | `3` | `.send()` retries before fallback |
| `DRAMATIQ_WORKER_THREADS` | per-lane | concurrency per worker service (set via the `--threads` flag in each lane's start command — see §12) |
| `WORKER_DB_POOL_MAX` | `8` | per-worker asyncpg pool ceiling (≥ that lane's threads) |
| `WORKER_DB_POOL_MIN` | `1` | per-worker asyncpg pool floor (keep low so idle lanes don't pin connections) |
| `OUTBOUND_RATE_LIMIT_PER_SEC` | (provider) | WindowRateLimiter cap |
| `WEBHOOK_JOB_MAX_RETRIES` | `5` | per-actor retries before DLQ |
| `WEBHOOK_DEDUP_TTL_SECONDS` | `86400` | idempotency guard TTL |

`max_retries`, `min_backoff`, `max_backoff`, `time_limit` are set per actor.

## 16. Generalizing to All Background Async Tasks

The pipeline is **not webhook-specific**. The same broker + actors + per-lane
workers form a general **background-task platform**. Webhooks were the forcing
function (the 502 incident), but delta product sync, escalation messages, Shopify
order-note/tag writes, message tagging, and any other deferred work map onto the
exact same machinery.

### 16.1 The rule: when to enqueue vs. run inline

Offload to a task when the work is any of:

- **(H)eavy** — meaningful CPU/DB/enrichment cost (delta sync, product upsert).
- **(N)on-critical to the response** — the caller doesn't need it done before
  replying (escalation send, message tagging, audit logs).
- **(E)xternal-I/O & rate-limited** — calls a throttled third party
  (Shopify Admin API, WhatsApp/Gupshup).
- **(S)cheduled/recurring** — cron-driven (delta product sync).

> ⚠️ **Don't over-queue.** Work the synchronous response *depends on* (must be
> reflected before you answer the user/agent turn) stays inline. Queuing adds
> latency + at-least-once complexity; reserve it for fire-and-forget / deferred
> / heavy / throttled work. This rule is what generalizes the §1 webhook fix:
> the 502 root cause was heavy work on a hot path — the same hazard exists on the
> agent-turn and cron paths, and the same fix applies.

This replaces today's fragile patterns — inline `await heavy()` on the request
path and fire-and-forget `asyncio.create_task(heavy())` (the audit-log hazard
PR #666 patched) — with **one durable, retried, observable** mechanism.

### 16.2 Three ways a task is produced (one way it's processed)

| Trigger | Source | Producer does | Example |
|---|---|---|---|
| **edge** | webhook route | `actor.send()` after HMAC/parse (§7) | inventory update |
| **schedule** | APScheduler cron | cron body just enqueues (§16.4) | delta product sync |
| **app** | agent turn / API handler | `actor.send()` instead of `await`/`create_task` | escalation, order note, tagging |

All three converge on the same actors, queues, workers, retries, DLQ, and
idempotency. Producing a task is always a cheap `actor.send(...)`.

### 16.3 Task → lane mapping

The new lanes added to §6:

| Task | Trigger | Lane | Priority | Key constraint |
|---|---|---|---|---|
| Delta product sync | cron | `product_sync` | low | per-client fan-out; off-peak |
| Escalation message to client | app | `outbound.escalations` | high | messaging rate limit; customer-critical |
| Update Shopify order note | app | `shopify.writes` | normal | per-shop API limit **+ per-order serialization** |
| Order tagging (Shopify) | app | `shopify.writes` | normal | per-shop API limit |
| Message tagging (internal) | app | `messages.tagging` | low | DB write; idempotent (set semantics) |

Lanes are grouped by **contended resource** (Shopify API, messaging, DB), so the
relevant rate limiter / pool governs *all* task types on that lane at once.

### 16.4 Cron integration — delta product sync (the "scheduled producer" pattern)

Keep **APScheduler as the trigger only**; move the heavy work into the worker:

```python
# Cron body (runs on the app loop) — cheap, no DB work:
@scheduler.scheduled_job("interval", minutes=15)
async def enqueue_delta_syncs():
    for client_id in await active_client_ids():     # light lookup
        delta_product_sync.send(client_id=client_id)  # fan-out, one job/client

# Worker actor (runs in worker-sync) — heavy diff + upsert:
@dramatiq.actor(queue_name="product_sync", priority=10,
                max_retries=3, time_limit=600_000)
async def delta_product_sync(*, client_id):
    if not await acquire_run_lock(client_id):        # idempotency / overlap guard
        return
    await run_delta_sync(client_id)                  # existing sync logic
```

Why this is better than today's in-process cron:

- Heavy delta work leaves the **web/app event loop** (today's APScheduler crons
  run in-process and contend for the same DB pool that serves requests).
- **Per-client fan-out** parallelizes across `worker-sync` threads at a bounded
  rate, instead of one long serial cron.
- Retries / DLQ / idempotency come for free.
- Optional **fan-in**: a Dramatiq `group(...)` of per-client jobs with a
  completion callback (e.g. emit a "sync complete" metric) when all finish.

> `periodiq` (pure-Dramatiq cron) is an alternative to APScheduler triggers;
> recommend keeping APScheduler initially (already in the app) to minimize churn.

### 16.5 App-triggered tasks — escalation, order notes, tagging

Provide one thin helper so call sites stop awaiting heavy work inline:

```python
# Instead of:  await send_escalation(...)   or   asyncio.create_task(...)
send_escalation.send(client_id=cid, conversation_id=conv, reason=reason)   # outbound.escalations
update_order_note.send(shop=shop, order_id=oid, note=note, op_id=uuid4().hex)  # shopify.writes
tag_message.send(message_id=mid, tags=tags)                                # messages.tagging
```

Each is a thin actor wrapping the **existing** business logic (same pattern as
the webhook actors in §8), so adoption is incremental — convert one call site at
a time behind the existing per-lane enable flags.

### 16.6 External-API rate limiting & write-safety (Shopify writes)

Order-note and tag writes hit the **Shopify Admin API**, which is throttled
(REST ≈ 2 req/s leaky bucket per shop; GraphQL cost-based). Two safeguards:

1. **Per-shop rate limit** — a Dramatiq `WindowRateLimiter` keyed on the shop
   domain wraps every `shopify.writes` actor, so order notes + tags + any future
   Shopify writes share one budget per shop. On HTTP 429, the Retries middleware
   backs off (honor `Retry-After`).
2. **Per-order serialization** — an order note is a **read-modify-write** field;
   two concurrent updates to the same order clobber each other (lost update).
   Guard with a `ConcurrentRateLimiter(limit=1, key=f"order:{order_id}")` (or a
   distributed lock) so updates to the *same* order are serialized while
   different orders still run in parallel. The `op_id` makes the write
   idempotent across retries.

The messaging lanes (`outbound.escalations`, `outbound.notifications`) reuse the
WhatsApp/Gupshup rate limiter from §11.

### 16.7 Priority classes

Map every task to a class; the class picks the lane/priority and keeps bulk work
from ever delaying customer-facing work:

| Class | Examples | Priority |
|---|---|---|
| Real-time / customer-facing | escalations, order & shipping webhooks, cart | high |
| Data integrity | product / inventory sync, Shopify writes | normal |
| Bulk / maintenance | delta sync, message tagging, audit logs | low |

### 16.8 Idempotency for non-webhook tasks

At-least-once delivery applies to *all* tasks, so each needs a key:

- **Delta sync** — `acquire_run_lock(client_id)` (overlap + duplicate-trigger
  guard); a late retry that finds a newer run already done is a no-op.
- **Order note / tag** — dedup on `op_id` (and per-order serialization §16.6) so
  a retried note isn't appended twice.
- **Message tagging** — naturally idempotent (applying the same tag set twice is
  a no-op).

### 16.9 Deployment impact

Two new worker services join §12 (same image, one queue each):
`ecommagents-worker-shopify-writes` and `ecommagents-worker-tagging`; escalations
run on the existing `worker-outbound` (or its own service if volume warrants).
All are small instances — the §9 connection budget already assumes
small-per-worker pools (`WORKER_DB_POOL_MIN=1`), so adding low-volume lanes stays
within `max_connections` headroom.

## 17. Observability (Grafana / OpenTelemetry / Loki)

Yes — and it reuses the stack you **already** run. The app exports via
**OpenTelemetry OTLP** today (`opentelemetry-exporter-otlp`, FastAPI/ASGI/logging
instrumentation, a custom `MeterProvider` in `monitoring/otel_metrics.py`), and
the original 502 incident was triaged in **Grafana + Loki**. Workers join the
same pipeline so the three signals — **metrics, traces, logs** — land in Grafana
with no new vendor.

> Design intent: the incident was only visible *at the proxy* (502s) after the
> damage was done. With this section, the trouble is visible **at the queue**
> (backlog rising, broker memory climbing) minutes earlier — and the same
> signals drive the §9 autoscale decision.

### 17.1 Metrics

Two complementary sources:

1. **Dramatiq's built-in Prometheus middleware** (ships with `dramatiq`,
   enabled by default). Per `(queue_name, actor_name)` it exposes: counters for
   total / errored / retried / dead-lettered messages, gauges for in-progress
   and delayed-in-memory messages, and a histogram of processing time — on
   **`:9191`** (`dramatiq_prom_host` / `dramatiq_prom_port`), with multi-process
   aggregation via the prometheus multiproc dir. There is an official
   **[Grafana dashboard #3692 "Dramatiq"](https://grafana.com/grafana/dashboards/3692-dramatiq/)**
   to import as-is.
   - Ship these to Grafana by scraping `:9191` on each worker with **Grafana
     Alloy / Agent** (or Grafana Cloud hosted scrape). Lowest-code path to the
     full built-ins + prebuilt dashboard.
   - *Consistency alternative (preferred here):* a small custom
     `OpenTelemetryMiddleware` emitting the same signals through the existing
     OTLP `MeterProvider` (mirroring `otel_metrics.py`), so workers need no
     scrape endpoint and everything flows through the one OTLP pipeline already
     in place. This is the path the
     [OneUptime Dramatiq + OpenTelemetry guide](https://oneuptime.com/blog/post/2026-02-06-monitor-dramatiq-task-queues-opentelemetry/view)
     uses end-to-end (one middleware emits both spans **and** metrics). Given the
     codebase already standardizes on OTLP, **lean this way** — and for our
     **multi-process, per-lane workers** OTLP push also sidesteps the Prometheus
     `prometheus_multiproc_dir` aggregation dance (each process just exports via
     OTLP; the backend aggregates). Keep the built-in Prometheus middleware +
     dashboard #3692 only if you also want the out-of-the-box panels with zero
     custom code. The middleware design is in §17.2.

2. **Queue depth + oldest-message age (we must add this).** The Prometheus
   middleware reports *in-progress* and *delayed-in-memory*, but **not pending
   backlog length** — which is the single most important signal here. Add a tiny
   periodic exporter (one coroutine, or a sidecar) that measures per-lane backlog
   and reads the tail job's `enqueued_at` to compute **oldest-message age**,
   emitted via the OTLP `MeterProvider` as a `dramatiq.queue.depth` gauge. This
   is the **primary autoscale trigger and alert** (§9).
   > ⚠️ **Don't copy the tutorial's key.** The OneUptime guide polls
   > `LLEN dramatiq:default.DQ` — but `.DQ` is the *delayed* sub-queue and
   > `default` is hardcoded. Probe the **correct per-lane key** for Dramatiq's
   > Redis broker layout (the pending list, not the delayed/acks structures);
   > confirm the exact key against the broker version at build time rather than
   > hardcoding a suffix.

### 17.2 Traces — one trace from edge → worker

FastAPI is already OTel-instrumented, so each webhook request starts a trace. We
want the worker's handler span to be a **child** of it, so a single trace spans
**receive → enqueue → process**.

- The job envelope already carries `trace_id` (from PR #666). Extend it to carry
  the **W3C `traceparent`**; a ~30-line producer/consumer middleware injects it
  on `send()` and extracts it + calls `set_trace_id(...)` on receive (reusing
  `trace_context`).
- **`opentelemetry-instrumentor-dramatiq`** (Shrest4647) exists and creates actor
  spans, **but** it is a third-party, single-maintainer package (v0.1.2,
  traces-only) — *not* official OTel-contrib (tracking issue
  [contrib#1916](https://github.com/open-telemetry/opentelemetry-python-contrib/issues/1916)
  is still open). **Recommendation:** prefer the small in-house middleware (we
  already have `trace_context` + the envelope); if you adopt the package, pin it
  and vet it, and don't rely on it for metrics.

#### In-house `OpenTelemetryMiddleware` (traces + metrics in one)

A single Dramatiq middleware, registered with
`broker.add_middleware(OpenTelemetryMiddleware())`, handles both signals — the
pattern the
[OneUptime guide](https://oneuptime.com/blog/post/2026-02-06-monitor-dramatiq-task-queues-opentelemetry/view)
documents. Hooks and what each does:

| Hook | Signature | Responsibility |
|---|---|---|
| `before_enqueue` | `(broker, message, delay)` | start a `dramatiq.enqueue` span; **inject** W3C context (`opentelemetry.propagate.inject`) into `message.options["otel_context"]` so the worker span chains to the producer |
| `before_process_message` | `(broker, message)` | **extract** context (`...propagate.extract`) from `message.options["otel_context"]`, start the *process* span as its child, `set_trace_id(...)`, stash span + start time on the message |
| `after_process_message` | `(broker, message, *, result=None, exception=None)` | record exception/status, **end the span, and emit the metrics** (duration histogram + success/failure counter) |
| `after_skip_message` | `(broker, message)` | close the span for skipped/dead-lettered messages with an error status |

Use OTel **messaging semantic-convention** attributes so any backend understands
them: `messaging.system="dramatiq"`, `messaging.operation` (`send` / `receive`),
`messaging.destination` (the queue name), plus `dramatiq.actor_name`,
`dramatiq.message_id`, `dramatiq.queue_name`, and `dramatiq.retries`.

Metric instruments (via the existing OTLP `MeterProvider`), names per the
guide: `dramatiq.task.duration` (histogram, ms) and
`dramatiq.task.success` / `dramatiq.task.failure` (counters), labelled by
`queue_name` / `actor_name` — complementing the `dramatiq.queue.depth` gauge from
§17.1(2).

> **Two refinements over the tutorial.** (1) The OneUptime middleware *declares*
> the duration/success/failure instruments but never actually records them in
> `after_process_message` — **ours must emit them there** (that's the whole point
> of the metrics). (2) The hooks are sync broker-level callbacks, so they wrap
> our **async** actors correctly under the AsyncIO middleware (the hook fires on
> the worker thread around the coroutine's execution) — no change needed for
> async handlers.

### 17.3 Logs — structured & correlated in Loki

- Workers log to stdout in the same structured format; the already-present
  `opentelemetry-instrumentation-logging` injects `trace_id`/`span_id` into
  records, so Loki ↔ traces pivot works.
- Every job log line carries `queue`, `actor`, `job_id`, `attempts`,
  `client_id`, `shop_domain`, `trace_id` — the same fields the incident triage
  relied on. Render log streams ship worker stdout to Loki / Grafana Cloud Logs.
- Emit explicit lifecycle logs: `received` / `succeeded` / `retrying (attempt n)`
  / `dead-lettered`, with `{e!r}` on errors (carrying forward PR #666's
  blank-`❌` fix).

### 17.4 Broker (Render Key Value / Valkey) metrics

- Memory, connections, and ops are in the **Render dashboard**. To get them into
  Grafana, **Render (Pro plan+) streams service metrics to an OTLP provider**
  (e.g. Grafana Cloud) — metric names like `render_service_memory_usage_bytes`
  ([Render metric streams](https://render.com/docs/metrics-streams)). No
  `redis_exporter` needed. (On a plan without streaming, run a small
  `redis_exporter` service pointed at `DRAMATIQ_BROKER_URL` and scrape it.)
- Watch: **memory used vs `maxmemory`** (with `noeviction`, nearing the cap means
  enqueues will start failing → inline fallback), **connected clients vs the plan
  cap** (§4.2 / §9 budget), and keyspace size.
- **Worker CPU/RAM** comes from the same **Render service-metric stream** per
  worker service — so we *don't* need the tutorial's `psutil`-based
  `health_check_task`; Render already reports per-service CPU/memory to Grafana.

### 17.5 Dashboards & alerts

Per-lane Grafana panels: queue depth, oldest-message age, processing rate,
p50/p95 duration, retry rate, DLQ count, in-progress, error rate; plus broker
memory % and connections %.

Alerts (these would have fired **before** the proxy 502s):

| Alert | Why |
|---|---|
| oldest-message age > N min | backlog not draining — also the §9 autoscale trigger |
| DLQ count / rate > 0 | jobs failing past retries — needs eyes |
| broker memory > ~70% | with `noeviction`, approaching enqueue failures |
| enqueue-failure / inline-fallback rate > 0 | broker trouble; fallback is load-bearing |
| (keep) existing 4xx/5xx alert | should now stay quiet — webhooks return fast |

### 17.6 Dependencies

- **Recommended:** the in-house `OpenTelemetryMiddleware` (§17.2) emitting spans
  + metrics through the **existing** OTLP exporter — no new dependency, no scrape
  infra. Reuses `trace_context` and the OTLP `MeterProvider` already in
  `monitoring/`.
- Optional add-ons: `dramatiq`'s built-in Prometheus middleware +
  `prometheus_client` with **Grafana dashboard #3692** if you want the prebuilt
  panels for free; `opentelemetry-instrumentor-dramatiq` (pinned) only if you
  prefer a package over the ~50-line middleware.
- Per-lane backlog panels (queue depth + oldest-message age) from §17.1(2).

WhatsApp API Versioning — per-client config & multi-layer cache

How a client is switched to the new Gupshup enterprise GatewayAPI, where the Client ID & Bearer token live, and how every read is cached. All config lives in one table: client_configs.

① Write — enabling a client (config only)

1
Ops/onboarding upserts two rows into client_configs for the tenant (one UPSERT per config_key, ON CONFLICT (client_id, config_key)).
2
whatsapp_api_version = "enterprise" flips the switch. Absent / anything else ⇒ legacy path, untouched.
3
gupshup_enterprise_details holds the userid (Client ID) + Bearer token (+ optional URL).
4
After write, bust the cache keys (or wait out TTL). No code deploy needed — it's data.
Tenant-scoped & isolated: every row keyed by client_id; the Bearer secret is never hardcoded and never logged.
